# Scopes

A scope is an opaque label (`[A-Za-z0-9._:-]{1,128}`) that separates the connections and run history of different
tenants, workspaces or environments inside one runtime. The runtime never interprets it.

## Model

- A runtime token is created with an immutable `scope`: `POST /api/runtime-tokens` with `{ "scope": "tenant-a", ... }`.
  To change it, create a new token and revoke the old one.
- A connection is stored with a scope: pass `scope` to `POST /v1/connections/:service/connect/api-key`,
  `/connect/custom-credential` or `/connect` (OAuth). The scope is fixed when the request starts and is stored with
  the pending OAuth state, so a callback cannot choose it. A reconnect keeps the scope of its target.
- Every lookup is confined to the caller's scope in the store itself: a scoped token reads only connections of its
  scope, and every request without a scoped token (an unscoped token, the static `runtimeToken`, JWT credentials,
  the administrator on `/v1/actions`) reads only unscoped connections. Existing single-tenant installs, whose
  connections are all unscoped, behave as before. A caller never sends a scope on `/v1`.
- Another scope's connection is never read, so it answers exactly like a connection that does not exist, whether it
  is selected by alias or by id, listed, searched or offered as a default.
- An empty `allowedConnections` list never widens a token beyond its scope.
- Connection names generated by `/v1` are random. A name that already belongs to another scope is rejected
  (`connection_scope_conflict`); only the administrator chooses names.

## Run history

Runs record the scope of the token that made them. `GET /api/runs?scope=...` lists one scope and
`DELETE /api/runs?scope=...` deletes it, so a tenant's history can be removed on offboarding independently of the
count-based `runLimit`.

## Transit files

Files that an action creates carry the scope of the token that ran it, on all four backends (local disk, S3, R2, KV),
and the executor can read back only files of that scope. A runtime token that has no scope sees only unscoped files.
`POST /api/files?scope=...` (admin) uploads a file into a scope.

`GET /api/files/:id` stays open for files that belong to no scope. A scoped file is served only to a bearer of the same
scope or to the admin token, and to anyone else it is `404 file_not_found`, the same answer as a missing file. A host
that hands a scoped `downloadUrl` to a browser must therefore proxy the download with the scoped token.
`DELETE /api/files/:id` follows the same rule.

## Deleting a scope

`DELETE /api/scopes/:scope` (admin) revokes the scope's runtime tokens, cancels its trigger subscriptions, disconnects
its connections (revoking OAuth grants), purges its runs and deletes its transit files. It answers `200` with the
counts, or `207` with a `failures` list when a step failed; call it again to finish. Nothing outside the scope is touched.

## Not covered yet

- Connection names are unique per service across scopes rather than per scope.
- Proxy calls are not recorded as runs, and runs carry no trace id.
- Deleting a scope leaves its idempotency records, which expire on their own.
- The console is an operator view and is not filtered by scope.
