# WeChat Store merchant operations

The `weixin_store` provider uses the connected merchant's AppID/AppSecret and the shared stable-token flow. These actions do not enable new permissions, publish content, or schedule daily work on their own. Check the merchant's actual access before using a capability. The permission-set numbers below describe WeChat third-party authorizations; they do not add third-party token support to this connector.

## Operating workflow

| Need                               | Actions                                                                                                                             | Important boundary                                                                                                                                                                                                                                                 |
| ---------------------------------- | ----------------------------------------------------------------------------------------------------------------------------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------ |
| Product content and purchase entry | Existing product/image actions; `get_product_h5_url`, `get_product_qr_code`, `get_product_tag_link`                                 | Only on-sale self-operated products. QR output is an image URL; tag links open inside WeChat. None publishes the material.                                                                                                                                         |
| Daily orders and stock             | Existing `list_orders`, `get_order`, `list_products`, `get_product`                                                                 | Retain unresolved ids and continue from the last successful cutoff. Order-query windows are at most seven days. An empty order list says nothing about traffic.                                                                                                    |
| Shipping                           | Existing `send_delivery`, carrier/address/freight reads; `update_delivery_info`, `send_exchange_delivery`                           | The new shipment/correction actions are writes. Supply real package information and obtain the approval required by your application. Corrections use package-level `change_infos`; the legacy whole-order replacement form is not exposed.                        |
| After-sales and disputes           | Existing after-sale list/detail/accept/reject; `list_aftersale_reasons`, `list_aftersale_reject_reasons`, `get_aftersale_complaint` | After-sale list windows are at most 24 hours. Follow old unresolved records; do not discard them because they leave a recent time window.                                                                                                                          |
| Evidence                           | `upload_aftersale_image` → existing `reject_aftersale.mediaFiles`                                                                   | Upload is a write. JPEG/PNG/BMP/GIF, up to 10 MB, scene 170. Use complete C2C URLs including query parameters. Rejection reasons with `need_proof = 1` require evidence. Already-uploaded C2C video references are accepted; video upload is not implemented here. |
| Merchant complaints                | `list_merchant_tickets`, `get_merchant_ticket`                                                                                      | Currently covers shipping-reminder tickets (class 9), not every platform notice. Preserve response deadlines and paginate with `start`, `limit`, and `total`.                                                                                                      |
| Traffic and conversion             | `get_compass_shop_overview`, existing `get_compass_product_data`                                                                    | Only T+1 historical days in Asia/Shanghai. Counts and money remain upstream strings; Compass money is in fen. No same-day traffic or profit inference.                                                                                                             |
| Reconciliation                     | `get_funds_balance`, `list_funds_flows`, `get_funds_flow`, `list_order_settlements`                                                 | Read-only. Funds flows appear after 16:00 the next day. Settlement amounts are in fen; balance/flow amounts retain the units supplied upstream. Pending settlement is not cash received or profit.                                                                 |

For funds flows, carry `next_key` forward, increase `page`, and keep `pageSize` unchanged. A cursor is mandatory at `page * pageSize >= 10000`. For order settlements, context pagination is enabled by default: pass `page_ctx` back as `pageContext` until it is empty. Set `usePageContext: false` explicitly for offset pagination. These actions return one page per call and do not silently collect or truncate a ledger.

Unavailable data, missing permission, an absent record, and provider failures remain errors. They are not converted into successful zero counts. Business failures on shipment/rejection actions are not automatically retried; the shared request layer only refreshes and retries a token rejected as invalid by WeChat.

Numeric response properties named `id` or ending in `_id` retain their numeric type when safely representable. Larger integer identifiers are returned as exact decimal strings taken from the raw JSON text, including settlement-linked order ids. Quoted ids, ordinary amounts and non-ID fractions retain their existing types. Unsafe ID representations that cannot be parsed as exact decimal integers fail instead of returning rounded identifiers.

The image-upload page's example still shows `scene_type=0`; the current enum and after-sale contract require `170`, which this action sends. Logistics correction follows the documented `change_infos` schema; individual orders may still be rejected by WeChat's state, eligibility, or correction-count rules.

This increment does not add withdrawals, bank-account changes, buyer address decryption/real-phone access, customer-service message sending, or a notification webhook receiver. Customer-service sending needs a separate inbound-session/event integration. General platform notices remain outside this ticket API's documented coverage.
