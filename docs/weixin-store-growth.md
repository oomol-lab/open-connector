# WeChat Store talent, promotion and product diagnostics

The first four read-only actions reuse the existing WeChat Store AppID/AppSecret connection and stable-token cache. They do not create a connection, invite a talent, change a commission, update a product, or buy traffic. POST is the upstream transport for these read operations.

| Action                                     | Scope and limitations                                                                                                                                                                                       | Official reference                                                                                                                    |
| ------------------------------------------ | ----------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- | ------------------------------------------------------------------------------------------------------------------------------------- |
| `weixin_store.list_league_promoters`       | Merchant alliance talent list, not platform-wide discovery. Page index starts at 1; page size defaults to 20 and cannot exceed 20. Follow `continue_flag`.                                                  | [Talent list](https://developers.weixin.qq.com/doc/store/shop/API/league/promoter/api_getpromoterlist.html)                           |
| `weixin_store.get_league_promoter`         | Exactly one known `talentAppid` or `talentSearchKey` (talent appid or Channels finder_id). Nicknames and third-party ids are not interchangeable with these identifiers.                                    | [Talent detail](https://developers.weixin.qq.com/doc/store/shop/API/league/promoter/api_getpromoter.html)                             |
| `weixin_store.get_compass_product_data`    | A valid YYYYMMDD date, yesterday or earlier in Asia/Shanghai (T+1). Counts, monetary strings and nullable ratios retain upstream representations; monetary values are in fen.                               | [Historical product data](https://developers.weixin.qq.com/doc/store/shop/API/compass/api_getshopproductdata.html)                    |
| `weixin_store.get_product_restricted_info` | Batch of 1–50 product ids. Scene 3 covers store home/talent windows and scene 7 covers alliance. Restrictions are diagnostic and do not change selling status. Upstream merchant quota is 100 calls/minute. | [Restricted scenes](https://developers.weixin.qq.com/doc/store/shop/API/channels-shop-product/shop/api_getproductrestrictedinfo.html) |

Merchant self-development uses the existing shop token. Alliance access must be enabled and the corresponding API permission approved. The official service-provider permission sets are 141 (alliance), 175 (Compass), and 129 (products); these are not OAuth scopes. A valid existing credential does not guarantee each merchant has API access.

Product ids are sent as JSON numbers because the upstream endpoints require them. Both numeric strings and numbers are accepted, but values exceeding JavaScript's maximum safe integer are rejected before network access to prevent silent rounding.

The mock suite exercises routing, pagination, identity selection, the China date boundary, raw response preservation, input rejection, permission/rate errors and token refresh. It does not establish any merchant's live eligibility, current restrictions, traffic, or talent availability. Live acceptance requires checking the intended merchant and permissions with its existing credential separately.

## Cooperation and plan operations

The workflow also needs the following six reads and two explicitly mutating operations. Implementing these operations does not grant an agent authority to execute them. The caller must enforce its own recipient, merchant-write and spending approvals; action metadata identifies the two writes.

| Action                               | Purpose and contract                                                                                                                                                                                                                                                                                          | Official reference                                                                                                                |
| ------------------------------------ | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- | --------------------------------------------------------------------------------------------------------------------------------- |
| `list_league_promoter_products`      | Cooperating talent's current window (`dataType: 2`) or last-30-day sold products (`dataType: 1`); page size at most 20. Inspect the actual product id to establish window placement.                                                                                                                          | [Talent product data](https://developers.weixin.qq.com/doc/store/shop/API/league/promoter/api_gettalentproductdata.html)          |
| `list_product_promotion_talents`     | Relationships for an existing product and plan; page size at most 10. A promoting relationship alone does not prove window placement.                                                                                                                                                                         | [Promotion talents](https://developers.weixin.qq.com/doc/store/shop/API/league/item/api_listspupromotiontalents.html)             |
| `get_product_audit_strategy`         | Store-wide listing switches, useful alongside product restrictions. Cannot reconstruct a historical delisting reason or identify who delisted a product.                                                                                                                                                      | [Listing policy](https://developers.weixin.qq.com/doc/store/shop/API/channels-shop-product/shop/api_getproductauditstrategy.html) |
| `list_product_promotion_plans`       | Find existing plan ids before inspecting or changing a plan; page size at most 20. Supports audience filters 100/200/300.                                                                                                                                                                                     | [Plan list](https://developers.weixin.qq.com/doc/store/shop/API/league/item/api_listspupromotionplans.html)                       |
| `list_league_products`               | Existing alliance products and eligibility states; page size at most 100 and `pageSize * pageIndex <= 5000`. The current request contract has no cursor.                                                                                                                                                      | [Alliance products](https://developers.weixin.qq.com/doc/store/shop/API/league/item/api_getitemlist.html)                         |
| `get_league_plan`                    | Existing plan status, restrictions and commission. Request audience type is 100/300; response `item.type` uses legacy 1/2/3 and must not be copied into a request.                                                                                                                                            | [Plan detail](https://developers.weixin.qq.com/doc/store/shop/API/league/item/api_getitem.html)                                   |
| `invite_league_promoter` (**write**) | One verified `promoterId` or deprecated `finderId`, never an inferred mapping from `talent_appid` or a third-party id. Obtain approval for the exact recipient. Duplicate/previously cooperating responses are conflicts; do not retry blindly after uncertain delivery.                                      | [Cooperation invitation](https://developers.weixin.qq.com/doc/store/shop/API/league/promoter/api_addpromoter.html)                |
| `update_league_plan` (**write**)     | Exact existing product/plan, audience type 100/300. Operation 1 requires commission percentage 0–90 and also activates; 2 delists; 4 activates. State-only operations reject commission fields. This action does not expose audience/timing edits, creation or deletion. Obtain approval and read back state. | [Plan update](https://developers.weixin.qq.com/doc/store/shop/API/league/item/api_upditem.html)                                   |

All alliance operations require the same merchant permission described above. Listing policy uses product permission set 129 for service-provider calls.

Commission units differ by endpoint: talent product data and promotion relationships return a 0–1000000 scale (1000000 = 100%), whereas plan detail and plan update use percentage points (50 = 50%). Preserve upstream read values and never copy a talent-data ratio directly into a plan update. A nonempty `fail_talent_appids` is a partial failure even with a successful top-level response.

## Operating flow and remaining boundaries

1. Check `get_product`, restrictions, listing policies, alliance eligibility and the existing plan. Existing product and stock actions already support inventory checks; a read does not authorize relisting.
2. Obtain candidates from the merchant's cooperation list or a separately authorized discovery channel. The official APIs added here do not provide a public platform-wide talent recommendation/search directory. A third-party account search result needs verified identifier mapping before any native invitation.
3. Inspect talent detail and relevant cooperating-talent product data. Prepare one exact invitation recipient and terms, then execute only after caller approval. Adding a cooperation relationship does not automatically add the product to a talent window or promise acceptance.
4. Inspect plan relationships and the talent's actual window-product list. Use existing plan changes only within approved terms; do not create another plan just because no traffic has appeared.
5. Read historical Compass product clicks/transactions, and existing `list_orders` / `get_order` for actual payments and fulfillment. Existing `send_delivery`, freight/address actions, and after-sale actions support fulfillment and returns, subject to their normal write authorization.

Incoming customer consultation automation requires a separately configured and verified customer-service callback receiver. This change does not add one or imply that consultations are being collected. Native merchant customer service remains the manual fallback; sending messages is not an unsolicited talent discovery channel. Similarly, historical delisting investigation requires callbacks recorded at the time; current policy snapshots cannot recover past events.

Pre-merge validation uses mocked requests only, including invitation and plan-update mocks. Existing live services and credentials are unchanged. Real merchant read acceptance and any separately approved merchant writes belong to a subsequent deployment/acceptance step.
